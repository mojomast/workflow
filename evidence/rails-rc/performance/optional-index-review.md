# Optional Rails attempt index — independent performance-delta review

**Safe to use `--attempt-index` in the fresh, private synthetic benchmark.** The indexed configuration met 500 ms p95 for authenticated HTTP assembly of 500 local-attempt rows in the supplied 100-sample run: **470.575 ms events, 184.800 ms view**. The option is off by default. The default unindexed endpoint did **not** meet that target in the comparison run. No deployed database was opened or changed in this review.

## Installer and fresh-ledger execution

- **Transaction and identity — B `scripts/rails_attempt_index.py:20–48`.** Requires an absolute existing file and canonical UUID; opens SQLite in `mode=rw` (no creation) with zero busy timeout. It sets and verifies `trusted_schema=OFF`, requires existing WAL mode, then obtains `BEGIN IMMEDIATE`. The UUID lookup, existing-definition check, bounds check and fixed `CREATE INDEX` occur under that writer lock. The SQL does not come from a caller. Only the expected definition is an idempotent no-op; a conflicting definition refuses. Successful creation explicitly commits; closing releases the lock and rolls back uncommitted work on failure/early return. Existing event and receipt rows are not rewritten by the DDL.
- **Limits — B maintenance owner.** Creation refuses more than 120,000 existing rows, more than 512 MiB of database pages, or under 1.5 GiB free on the parent volume. A progress handler checks a ten-second deadline every 1,000 SQLite VM operations. These are preflight limits, not a space reservation or a hard wall-clock bound on storage I/O. A UUID identifies the ledger lineage, not a unique physical file: a restored copy has the same UUID. The tool assumes a trusted operator-selected path and private directory; it does not reject symlinks, verify filesystem ownership, validate the whole chain, or quiesce existing readers. `BEGIN IMMEDIATE` excludes competing writers during the change. Each client accessing an indexed DB must support JSON schema expressions with its normal hardened SQLite settings. No need to relax `trusted_schema`.
- **Benchmark isolation — W `scripts/bench_rails.py:105–131,289–309,317–329`.** The CLI accepts a scratch parent, not a ledger path. It makes a private temporary directory, initializes `synthetic.sqlite`, reads its UUID, closes the initializer, and invokes the sibling installer with that UUID **before** spawning the ten producers. It requires the exact `installed` outcome (with a 20 s subprocess timeout) and records `config.attempt_index`. Future writes maintain the index. Seed elapsed time includes the ongoing index maintenance but starts after empty-ledger index creation; it is not the cost to backfill an existing database.
- **Independent check.** From exact detached commit bytes, the installer regression passed on SQLite 3.46.1: wrong UUID, reduced row bound, busy writer, idempotence, unchanged query wire output, and a subsequent append/read under hardened schema settings. A fresh exact-tuple smoke with `--attempt-index --events 5000 --samples 1 --soak-seconds 0` completed, recording ten distinct writer processes and 5,000 unique seed IDs; the temporary ledger was removed. `index-smoke.Nx9om5/smoke.json` records the option and the intentional stream skip. The smoke establishes safe wiring, not a new latency or soak claim.

## What the HTTP evidence establishes

I checked `perf/http-index/measure.py`, the three completed reports, `index-cost.json` and the ten lane receipt files. The measured DDL string is byte-for-byte the installer's fixed SQL. The HTTP experiment added that DDL directly to a **populated synthetic backup**; it is not a timing of the installer's identity, limit or timeout checks. The reported DDL time was **715.9 ms**, and main-file size after checkpoint grew **15,212,544 bytes**. The planner changed from primary-key range search to `rails_local_attempt_scan`. All three health receipts agree on the ledger identity, ingest head **100,106** (100k seed + 106 later observations), O commit, R01 contract and runtime revision; the reported runtime-manifest digest matches the O Git blob.

These are actual authenticated loopback R12 GETs: a fresh HTTP connection and normal short reader snapshot per physical response, 401 for the no-bearer health control, 32,768-byte response bound. I recomputed the nearest-rank p95s and counts from the raw series. The 100-sample run per surface rotates ten lanes through offsets 0–4,500, after ten discarded first-page warmups. Events used **1,060** physical responses (10–11 per logical 500); views used **400** (4 per logical 500). Indexed maxima were **483.997 ms** and **192.238 ms** respectively. This is neither a single 500-row wire response nor a shared-Python-reader timing.

**Response identity:** the receipt files cover every original seed sequence exactly once. `measure.py:49–66` verifies each logical page's exact ordered event IDs against those receipts, checks partial coverage and the missing source, and follows the returned continuation. I independently matched every paired body-and-next-cursor digest in the 10-lane A/B (**20/20** across both surfaces) and the same first ten samples per surface of the 100-run. Events use the body bytes; views normalize only `generated_at` before reserialization. The deeper 90 pages per surface passed the benchmark's ID/coverage checks, but there is **no 100-page unindexed series** proving byte parity at those offsets. The profiled 10-sample indexed event tail already exceeded 500 ms; no general SLA follows.

**Disposition:** no blocker for the opt-in synthetic benchmark. Attribute the result to local `attempt` queries on this indexed, stationary fixture. Imported histories, other selectors, concurrent writes during HTTP pagination, browser latency, full indexed soak, physical SSD, and existing-deployment compatibility are not established by `perf/http-index`. Keep the default performance figures and any indexed write/soak results separate. This review changed no repository source.
