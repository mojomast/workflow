# BundleBees: interrupted initial ref publication

**Disposition: fixed for the hosted crash-B queue → normal tick path. Not fixed as a rule across all recovery entry points.** The normal tick recovered the original tested commit after interruption and refused a ref that had actually been deleted or moved after publication. Explicit `job recover --repo` and direct integration replay can still recreate a deleted ref before the job has recorded acceptance.

Reviewed Git objects: candidate `b1fa75b4b0a80d48feec134386c96cc1775c5ab8`, direct parent `399bf918cbb5b3a9223c4597b587cb34f55de18c`. All line references below are to the candidate. Tests ran against local Git archives and disposable repositories.

| Finding | Disposition and evidence |
|---|---|
| Interrupted first publication | **Closed for normal tick.** The coordinator puts the tested commit under a pending ref named from the request and result binding, seals the proof, then reaches `wave.after_persist` (`bundlebees_plugin/integrate_job.py:396–411,953–974`). Restart verifies the sealed request and proof, job scope, current verified attempts, execution identity, passing wave, commit ancestry and tested tree (`job.py:1457–1500`; `integrate_job.py:326–365`). One Git transaction compares the destination's old OID (zero for first creation), writes the tested head, and deletes the pending ref only if it still points at that head. The signed job save holds a verify lock on that same ref (`job.py:1501–1504`; `integrate_job.py:379–393`). |
| Deleted or moved after publication | **Closed for normal tick.** Publication consumes the pending ref. Normal tick sets `repair_ref=False` (`job_cli.py:415–426`); without the marker, only a destination already at the tested head is acceptable (`integrate_job.py:402–419`). Two successive ticks after deletion left the ref absent. Two after movement to the base left it at the base. In both cases the job stayed verified, with no acceptance. |
| Queue exception classification | **Closed for the reported false “job does not exist”.** Both claim paths use the same existence lookup (`queue.py:476–483,530–539,616–623`). It reads the sealed job with `recover=False`, returns `None` only for `JobError(code="job_missing")`, and propagates other errors. In an active-claim fixture, absence led to `needs_approval`; malformed JSON raised `job_invalid`; a MAC mismatch raised `job_tampered`. The latter two left the claim and card unchanged. No case dispatched work. The separate completion check still treats load failure as a reason to withhold acceptance (`queue.py:560–566`). |

**Residual — High for any cross-entry-point no-recreation guarantee.** In two independent `crash_state` fixtures, the initial ref had been published, the pending ref consumed, and the signed job save had not yet happened. After a real Git deletion, normal tick refused twice. On the same state that tick had refused:

- Explicit `job recover --repo` **recreated the deleted ref and persisted acceptance**. It calls `recover_integration` with its `repair_ref=True` default before checking settled history (`job_cli.py:108–113`; `job.py:1425–1428,1498–1504`).
- Direct `integrate()` replay **recreated the deleted ref** and returned the earlier accepted result without saving the job (`integrate_job.py:844–856`). This call also leaves repair enabled.

Both used the same fallback (`integrate_job.py:413–419`): a missing initial ref equals its recorded predecessor, also absent. The sealed receipt was valid and both restored exactly the tested OID; **what was missing was evidence that publication was still pending**. The fallback does not authorize an arbitrary different head. This finding concerns the interval before job acceptance is saved, not settled job history. Likewise, a crash before the proof is sealed is outside the successful crash-B window: the marker alone is insufficient. These are local process-restart results, not a power-loss or independent-ref-writer guarantee.
