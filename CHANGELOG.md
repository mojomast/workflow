# Changelog

## Unreleased

- The lease/tamper gate's non-slice rule gains a **review carry-forward**: an independent review recorded at an earlier head still counts when every commit after it is a merge of the base and the pull request's diff against the base is byte-identical (same paths, same blob shas, `--raw --no-renames`). A GitHub branch update forced by `strict_required_status_checks_policy` therefore no longer demands a re-review of unchanged code, while an authored commit, an unrelated merge or any content change fails closed with a named reason (`review_not_ancestor`, `review_carry_authored_commit`, `review_carry_unrelated_merge`, `review_carry_content_changed`, `review_carry_unreadable`). `docs/32-lease-tamper-gate.md` describes the rule; `tests/test_lease_tamper.py::BaseMergeReviewCarryTests` covers the four refusals and the two acceptance cases.
- The observability collector's worker usage view also reads the Rails ledger's `imported_origin_rows`: a peer launcher's `usage.observed` receipts are committed there as verbatim origin evidence (never into the ledger's own `event_rows`), so `usage.by_role.worker`, `usage.bee` and `usage.tokens_per_verified_patch` now report the real bee tokens instead of a measured zero. Receipts from both stores deduplicate by chain and dedupe key, a ledger without that table still reads `event_rows` only, and the origin scan is cached per ledger/WAL identity so a long-lived collector pays it once per ingest.
- Wave F design (`docs/design/wave-f-ab-harness.md`): an A/B harness scored by `tokens per verified patch`; one variable per experiment, `120 attempts per experiment` (20 tasks x 2 arms x 3 runs), and F1 gates the memory canary W2-G.

- The observability deploy metric now counts merged-but-not-deployed drift, not open pull requests: `bottlenecks.open_prs` reports PRs independently, while `deploy_debt`, deploy-stage `queue_depth` and invariant `awaiting_deploy` come from four read-only parity surfaces — `plugin` (checkout HEAD), `collector` (deployed collector bytes), `obs_app` (deployed Observatory app bytes) and `hyvv` (its deploy marker), each compared with `origin/main` using the `scripts/deploy_parity.py` revision or SHA-256-prefix semantics. `gateway_loaded` is not a surface in this metric. A missing repository, deployed file or marker, or a malformed/truncated marker makes that row `unknown`; any unknown row makes total debt and `awaiting_deploy` null (`partial`, or `unavailable` when all four are unknown), never parity, drift or zero. Parity rows have no drift timestamp, so deploy oldest-item age stays null and dwell/throughput stay unknown; the 12-hex file-digest comparison is the existing parity convention, not a full-content collision-resistance guarantee.
- The observability collector's usage totals denominator now counts usage-bearing rows only: `totals.requests` requires at least one resolved token count greater than zero, while `source.record_count` stays the raw parsed-record count and `unknown_cost_records` is restricted to usage-bearing rows; per-model and per-repo `requests` still count records seen. The owner also retired the zoo free pass as dead: no post-expiry price exists, and the $0 free-tier price rows belong to the app/snapshot side, not the collector (which has no pricing code; cost comes from ledger records).
- `totals.tokens_status` and `totals.cost_status` now count only usage-bearing rows in their numerators, so explicit-zero non-request rows can no longer turn `tokens_status` into `partial` or let a zero-token priced row make `cost_status` claim `known` while `unknown_cost_records` is non-zero; `totals.cost_usd` still sums every ledger cost, including zero-token priced rows.
- The observability collector gains an additive worker usage view: `usage.by_role` (coordinator and unknown from the existing `bee.usage/v1` rows, worker from the Rails ledger), `usage.bee` (worker `usage.observed` receipts deduplicated by chain and dedupe key, with token in/out/thinking by model and by repo) and `usage.tokens_per_verified_patch` (worker tokens over distinct verified attempts, with numerator, denominator, rule and basis). It takes optional `--rails-ledger PATH` and reads that SQLite ledger read-only (`file:...?mode=ro`, `PRAGMA query_only=ON`); worker cost stays null because launcher receipts carry no price, and `unknown_cost` counts the usage-bearing worker rows. The repo join is `<state-dir>/deliveries/<attempt_id>.json` -> `repo`; attempts without a delivery record land in the literal `unknown` bucket. The new schema properties are optional, so older snapshots still validate.
- The decision queue adds the frozen owner-decision receipt contract (`rizzstack.owner-decision-receipt/1`, signed with HMAC-SHA256 over the canonical receipt using the owner-held `BUNDLEBEES_APPROVAL_SECRET`), verifies it without ever reading or storing the key, and accepts it as evidence in `record_decision` and a new `verify-receipt` CLI verb. Refusals are named: `receipt_unknown_field`, `receipt_missing_field`, `receipt_bad_version`, `receipt_bad_id`, `receipt_bad_digest`, `receipt_bad_timestamp`, `receipt_bad_outcome`, `receipt_not_owner`, `receipt_key_missing`, `receipt_signature_invalid`, `receipt_binding_mismatch`, `receipt_decision_mismatch` and `receipt_bad_file`. A verified receipt is evidence only; the queue never applies a decision.
